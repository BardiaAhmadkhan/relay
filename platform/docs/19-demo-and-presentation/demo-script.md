# Five-minute demonstration and Q&A

Prepared **2026-10-26 (UTC)**. This is a rehearsal script, not evidence that the demonstration has been run or timed. Replace conditional lines with verified implementation facts after the final build rehearsal.

## The narrative

**“The useful question is what the evidence allows us to do next.”**

Relay helps a rider collect a useful record and helps an assessor see what is known, suspected and missing. Its distinctive moment is a clear human handoff and a conservative hard case, not an automatic “safe” verdict.

Before the event, call this a **pre-event experimental app**. On competition day, disclose reused preparation materials and follow the organizer's agreement. Do not present this preparation code as newly built that day.

## The analysis-mode fork

Select the truthful version at rehearsal:

- **Real cloud observations verified:** “These photographs are being analysed now. The response is checked before our policy rules use it.” Show the actual latency; do not claim a representative time from one run.
- **Local category-only model:** “This local model helps identify the broad item category. It does not assess protective condition, so the result goes to human inspection.” Demonstrate real image processing without implying unavailable condition analysis.
- **Network/provider unavailable:** “The service is unavailable, so the app keeps the evidence and gives a recovery path. It does not invent a successful assessment.” Continue with an explicitly labelled recorded run if permitted.
- **Example fixture:** “This is a labelled example used to show the interface and policy branch.” Never describe it as live inference.

A hard case is not a staged surprise: label its facts and its origin. Use only owned, consented or appropriately licensed photographs. Do not crash or damage equipment to create a demonstration.

## Measurement wording template

“On **[date/build]**, we ran **[N]** cases from **[source/licence and scope]** on **[device/service/model]**. **[Metric]** was **[actual value and denominator]**. **[Count]** cases remained unresolved. The measured processing interval was **[definition]**. Cost was **[measured or estimated, currency and inputs]**. This is an experimental sample, not a protective-safety accuracy claim.”

Do not present these until recorded:

- “100% accurate” based on a safety-rule test suite.
- A category-classification score as a condition-detection score.
- One successful run as typical latency.
- Formula-based API cost as invoiced spend.
- Synthetic fixtures as realistic gear evaluation.
- Browser preview as proof of iOS and Android camera readiness.
- An expert review screen as a connected expert service.
- A beautiful interface as evidence of rider preference.

## Q&A preparation

**Can it tell whether gear is safe?**

No. It collects and organises evidence for review. Protective performance and hidden condition are not established by photographs.

**Why not let the model approve an offer?**

The brief imposes hard exclusions, and the business decision requires facts beyond image appearance. Independent policy rules preserve these limits.

**What if someone lies?**

A photo cannot establish truthful crash history. We preserve disclosures and contradictions, and do not claim fraud-proofing. Human verification remains necessary.

**What if the model misses damage?**

A no-concern observation is limited to the supplied photographs and the model's capability. It is not proof of absence. Evaluate misses using an independently labelled case set and preserve the physical-inspection requirement.

**Why multiple photographs?**

They may provide complementary evidence. The starting recipe is a hypothesis being tested against effort and expert usefulness; more images are not inherently better.

**What is unique?**

The integration: guided evidence, source-aware corrections, hard policy boundaries, useful uncertainty and a refined mobile journey. Claims of improved speed or review quality require the planned comparison.

**What does it cost?**

Report measured calls/costs and explicit estimates from the final run. Separate local compute, hosting, failed calls and paid provider analysis.

**Does it work on both platforms?**

State the exact devices/builds exercised. Cross-platform source or a browser run is not enough to claim native camera validation.

**Who receives the brief?**

Name only the actual implemented destination. If no service is connected, say it is a local review record; do not imply a staff queue exists.

**What was built before the event?**

Explain the preparation branch, research and experiments. Use only what the agreement permits, and identify the competition-day work honestly.
